Chapter 04

🧩 技術選定・インフラ

言語・フレームワークと、動かす環境を決める。ADRで判断を記録し、秘密情報を安全に扱う。枯れた技術ほどAI生成の品質が上がる。

AI時代の選定基準

従来基準（成熟度・エコシステム・習熟）に加え、AI開発では「学習データの豊富さ」が新しい軸になる。広く使われ安定したAPIを持つ技術ほどAIの提案が正確。新しすぎる・ニッチすぎる技術は、古いAPIや存在しないメソッドを“それらしく”生成しやすい。奇抜な選定は支援効率を下げる。

ADR — 決定を記録する

技術・インフラの選定は ADR（Architecture Decision Record）として記録する。構成は固定: 比較表 → 決定 → 受け入れたデメリット。候補は最大3つ、推奨を必ず1つ。選択肢を並べるだけで終わらせない。

言語・フレームワークのデフォルト

用途デフォルト理由
WebフルスタックTypeScript + Next.js型がフロント/バックを貫通、情報量最大
API単体Hono または FastAPI軽量・型安全・ドキュメント自動生成
CLIPython (uv)依存解決が速く再現性が高い
並行処理Go並行モデルが単純で堅牢

環境は3層、差分は環境変数のみ

local / preview / production の3層をデフォルトとし、設定差分は環境変数のみで吸収する。コードやインフラ定義を環境ごとに分岐させない（分岐は事故の温床）。

秘密情報をコミットしない

ファイル内容git
.env.exampleキー名のみ（DATABASE_URL=）コミットする
.env実際の値gitignore
本番の値実際の値プラットフォームのSecret管理

ローカルのミドルウェア（DB等）は compose.yaml で起動する。

インフラの方針

  • IaC化が理想（Terraform 等）。手動構築の場合も再現手順を必ず文書化する。
  • マネージド優先でコスト・運用負荷を下げる（Vercel + Neon / Upstash / Supabase 等）。
  • Vercel利用時: Fluid Compute をデフォルト。DBは Marketplace（Neon / Upstash）か Supabase。
  • Supabase利用時: RLS を有効化し、アプリ側認可だけに依存しない（多層防御）。
  • コストは無料枠終了後の月額を併記し、予算アラートを設定する（従量課金は関数実行・egressで跳ねやすい）。

完了条件（チェックリスト）

  • 主要な選定論点ごとにADR（比較表・推奨1つ・受け入れたデメリット）がある
  • 候補が3つ以内に絞られている
  • local / preview / production の3層が定義され、差分が環境変数のみ
  • .env.example がコミットされ、実値はコミットされていない
  • IaC または再現手順が文書化されている / STATUS.md 更新済み
落とし穴: AIの知識にはカットオフがある。新しいFW・SDKでは古い書き方や廃止APIを提案しうる。新しめの技術は公式ドキュメント/移行ガイドを一次情報として併読させ、バージョンまで指定する。また生成したデプロイ設定に実値の秘密が直書きされることがある — シークレットスキャナをCIに入れて機械検出する。
