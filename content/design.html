Chapter 03

📐 設計

承認済み要件を、実装可能な構造へ落とす。データ・API・UI・アーキテクチャを一貫した方針で決め、全要件を設計に対応づける。AIが盛りがちな過剰設計を意図的に抑える。

図はすべてMermaidでテキスト管理

ER図・シーケンス図・構成図はMermaidで書き、リポジトリに置く。画像ファイル（PNG/draw.io等）は差分管理できずレビューできないため禁止。テキストならPRで差分が見え、AIも読んで更新できる。

ディレクトリ構成

設計資料は docs/02_design/ にまとめる。データ・API・シーケンスを種類ごとに分け、シーケンス図はユースケース単位でファイル分割する。

データ設計

  • 第3正規形をデフォルト。非正規化（性能目的の冗長保持等）は理由を明記する。
  • 論理削除（deleted_at）をデフォルト。物理削除は理由を明記（監査・復旧要件と衝突しないか確認）。
落とし穴: 論理削除を採用したら、全参照クエリに WHERE deleted_at IS NULL が必要。AIは集計・JOIN・ユニーク制約で削除済み行を巻き込みやすい。共通スコープ/ビューで強制すると漏れにくい。

具体例: 方針を渡してER図を生成させる

API / レイヤー設計

バックエンドの構造は実装前に決める。ルーティング / ユースケース / ドメイン / インフラの層を分け、副作用を外周（インフラ層）に寄せる。下図は1リクエストが各層をどう通るかの責務分担。

  • REST/RPCのスタイルを統一。バージョニング・ページネーション方式（cursor/offset）・エラー形式（{code, message, traceId}）を最初に決める。後から変えると破壊的変更になる。
  • 型安全をAPI境界まで貫通させる（OpenAPI / tRPC / zod）。サーバ⇄クライアントで型を二重管理しない。

UI / 情報設計

フロントを持つなら、画面に入る前に情報構造とUIの土台を決める。

  • 情報設計: 画面階層・ナビゲーション・主要導線を決める。
  • デザインシステムを先に決める（shadcn/ui 等）。トークン（色・余白・タイポ）と共通コンポーネントがあれば、AIが一貫したUIを量産できる土台になる。
  • 4つの画面状態（ローディング / エラー / 空 / 権限なし）を設計段階で各画面に織り込む。実装で抜けやすい（05 開発・実装）。

アーキテクチャは複雑さに見合わせる

セキュア・バイ・デザイン

セキュリティは後付けでなく設計に織り込む（横断テーマの詳細は 09 セキュリティ）。

  • 認証と認可を分離して設計する。認可はリソース単位でチェックする前提を、API設計に最初から入れる（IDOR対策）。
  • 機密データの保存（暗号化・最小保持）と、ログに出さない方針を決める。
  • 信頼境界を明確化（外部入力をどこで検証するか）。

トレーサビリティと YAGNI

  • トレーサビリティ表（全機能要件 → 設計のどの部分で実現するか）を含める。要件と設計の抜け漏れを機械的に検出できる。
  • YAGNI — 要件にない機能を設計に入れない。将来案は「拡張余地」メモに留める。AIの「念のため」の汎用化は、各抽象に「今の要件のどれを満たすか」を問うて削る。

完了条件（チェックリスト）

  • ER図・API/レイヤー図・主要シーケンス図がMermaidで存在する
  • 正規化方針・削除方針が明記されている
  • API契約（形式・バージョニング・ページネーション）が決まっている
  • （UIあり）情報設計とデザインシステム方針がある
  • トレーサビリティ表で全要件が設計に対応づいている
  • アーキテクチャ選定の理由が書かれている / STATUS.md 更新済み
AI活用: 設計レビューでAIに「カバーできていない要件」「過剰な抽象」「認可が漏れる箇所」を問うと、トレーサビリティの穴・オーバーエンジニアリング・設計段階のセキュリティ欠陥を同時に洗い出せる。
